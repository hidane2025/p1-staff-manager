## 改訂の履歴

| 版 | 主軸業務 | 却下された理由 |
|---|---|---|
| v1 | 見積書の作成 | 業界が偏る（製造・建設）＋「AIで見積」に意外性がゼロ |
| v2 | 採用の応募者対応 | **ATSの標準機能と被っていた**（無料ATSにも搭載） |
| **v3** | **引き継ぎ・教育** | — |

**v2の失敗が、この設計で一番の学びになった。** → [条件5の追加](#条件5)

## 球として使える5条件

| # | 条件 | 満たさないとどうなるか |
|---|---|---|
| 1 | どの業界にもある | 業種ごとに台本を作り直すことになる |
| 2 | 社長が痛みを知っている | 受付を突破できない・決裁が動かない |
| 3 | 「AIでできるの!?」の意外性がある | 「AIで効率化」と同じ扱いになり、聞き流される |
| 4 | ヒダネが実際にやっている | 見せてくださいと言われた瞬間に終わる |
| **5** | **既存ツールの標準機能と被っていない** | **「うちもうやってます」で信用ごと失う** |

<a id="条件5"></a>
### 条件5が抜けていたのがv2の失敗

```
社長「それ、うちのATSがもうやってますけど」
     ↓
この電話だけでなく、ヒダネという会社の評価が下がる
```

条件3（意外性）が欠けているだけなら「刺さらなかった」で済む。
**条件5が欠けていると「何も調べずに電話してきた人」と判断される。損失の質が違う。**

無料ATS（Airワーク採用管理、リクナビHRTech、Hirehub、yoiwork 等）が普及しており、
**応募者への自動返信も面接の日程調整も標準機能**。20〜100名の会社でも既に解決済みの可能性が高い。

→ 既存ツールとの被りチェック表は [03_刺さる業務カタログ.md](03_刺さる業務カタログ.md)

## 結論：4つの設計判断

### 判断① 「AI社員」は**証拠**として使い、**商品**として売らない

| | |
|---|---|
| ✕ | 「AI社員を導入しませんか」→ 商品の輪郭が曖昧なまま話が進み、商談で崩れる |
| ◯ | 「うち社員3人しかいないんですけど」→ **自己紹介**であり、提案ではない |

ヒダネの収益の中心は研修。AI社員導入は「本当にやっている会社だ」という**証明**としては最強だが、単体商材としては定義しきれていない。フックと売るものが乖離すると「釣り」になる。
そして電話口で「研修です」と言えば即切られる。**電話では商品を売らない。売るのは次の30分だけ。**

---

### 判断② 主軸業務は「**引き継ぎ・教育**」

#### なぜここか

| # | 条件 | 引き継ぎ・教育 |
|---|---|---|
| 1 | どの業界にもある | **◎** 人が辞めない会社はない |
| 2 | 社長が痛みを知っている | **◎** ベテラン退職時の最多の懸念は「問題発生時に誰も解決できない」 |
| 3 | 「AIでできるの!?」の意外性 | **◎** 手順ではなく**判断**が移せる、は想像しにくい |
| 4 | ヒダネが実際にやっている | ◎（要・運用確認 → [前提条件](#前提条件)） |
| 5 | **既存ツールと被っていない** | **◎ ここが空いている** |

#### 既存ツールが解決できていない理由

マニュアル作成ツール（Teachme Biz、tebiki 等）は**手順**を残せる。
でも **「どういう時に、どう判断するか」は手順書に書けない**。

```
書ける   ： この機械はこのボタンを押す
書けない ： この客からこの条件で来たら、受けない
書けない ： この症状が出たら、たぶん◯◯が原因
書けない ： この見積は、いつもより1割乗せる
```

**そして「暗黙知の形式知化」は、誰もができていない**（書く時間がないから）。

#### さらに、ヒダネの本業と完全に一致する

**「教える」を売っている研修会社が、「教える」をAI化した話をする。**
これ以上ない整合性。しかも社員3人という規模が、その必然性を証明している。

---

### 判断③ インパクトは「説明」ではなく「**事実 → 矛盾 → 種明かし**」で作る

```
✕ 「AIで業務を自動化してます」
   → 説明。想像できる。「AIで効率化」の棚に入れられて終わり

◯ 「うち、引き継ぎってものがないんです」            ← ① 不可能に聞こえる事実
   （一拍）
   「人が辞めても、次の人がその日から同じことできます」← ② 矛盾
   「その人の判断の仕方だけ、AIに移してあるので」      ← ③ 種明かし
```

**「AI」という単語を必ず最後に置く。** 先に言うと、相手の頭の中で「またAIの営業か」という既存の棚に分類されてしまう。

そして **「手順書だと書けないんですよ、そこは」** を必ず添える。
既存ツールとの違いを、相手が聞く前に自分から示すため。

---

### 判断④ 受付突破は「**求人の件**」で権限外に持ち込む（v2から変更なし）

ここは機能する設計なので触らない。

```
お世話になります。名古屋のヒダネと申します。

御社の求人の件でお電話しました。
Indeedに出されている「製造スタッフ」の募集を拝見しまして、
1つだけお伺いしたいことがあります。

社長さん、いらっしゃいますでしょうか。
```

| 要素 | 効き方 |
|---|---|
| 「求人の件」 | **人事案件は受付の権限外。**判断できないので上げるしかない |
| 「Indeedの**「製造スタッフ」**の」 | **固有名詞。**実際に見てきた証拠。一斉架電ではないと分かる |
| 「1つだけ」 | 短いと分かる |

**そして求人は、本題（教育）への入口としても機能する。**

```
求人に「未経験可」        → 「教えるのは誰がやられてます？」
求人に「経験者優遇/必須」  → 「教える余裕がないから、という感じですか？」
同じ職種を3か月以上掲載    → 「応募が来ないんですか？入っても続かない感じですか？」
```

**3つ目が最強。** どちらに転んでも話が進み、「続かない」なら教育の話にど真ん中で入る。

```
 ①リスト作成          ②仕込み            ③架電           ④アポ           ⑤商談
 hidane-teleapo-list → 求人を読む    → 求人の件で   → 実演30分     → 提案
   ＋求人の有無         4パターン判定    受付突破        業務を1つ
                                           ↓            AIに移す
                                     教育コストを          ↓
                                     数字で出す      その担当者の職務が
                                                       特定される
                                                          ↓
                                                   そのまま計画届に載る
```

## アポの切り方

> **「御社の業務を1つ、その場でAIに覚えさせる30分」**

```
1つは、御社の業務を1つ選んでいただいて、その場でAIに覚えさせるところをお見せします。
もう1つは、今の教育に何時間かかってるかを御社の数字で出します。

それだけ持ち帰っていただければ、それで結構です。売り込みはしません。
```

**「その場でAIに覚えさせる」が肝。**
相手は「AIで効率化」を100回聞いている。でも**自社の業務がAIに移るところを見た人はほぼいない**。

## 使う数字

| 場面 | 数字 |
|---|---|
| 教育コストの可視化 | **「1人採ると、実質もう1人分の手が3か月消える」**（相手に計算させる） |
| 採用コストの参考 | 中小企業（3〜300人）の採用単価は**30万円台前半** |
| 属人化のリスク | ベテラン退職時の**最多の懸念は「問題発生時に誰も解決できない」** |
| 構造的な背景 | 製造業は「**人がいないため育てられない**」（ものづくり白書2026） |

<a id="前提条件"></a>
## ⚠️ この設計を使う前提条件

```
「引き継ぎってものがないんです。判断の仕方だけ、AIに移してあるので。」
```

**ヒダネが実際にやっていて初めて使える。**
商談で「見せてください」と言われる。そのとき出せないものは、電話で言ってはいけない。

### まだやっていない場合の手順

```
1. ヒダネの業務を1つ選び、判断基準ごとAIに移す
   （例：商談前リサーチの進め方、提案書の作り方の判断）
2. 実際に「別の人がその日からできる」状態を作る
3. その事例を持ってから架電を始める
```

**運用実績のない台本は使わない。** 設計上の前提であって、努力目標ではない。

## KPI

BtoBテレアポの相場は**アポ率 0.5〜3%**、コンタクト率 30〜40%。

| 指標 | 目標 |
|---|---|
| 架電数 | 100件 |
| 接触 | 35件（35%） |
| 決裁者に到達 | 10件（10%） |
| **アポ獲得** | **2〜3件（2〜3%）** |

```
1受注 = 5アポ = 約200架電
1受注の売上 = 5名 × 40万円 = 200万円
→ 架電1件あたりの期待値 ≒ 1万円
```

**仕込みに1社5分。現実的には 1日30〜40件（仕込み込み）が上限。**

```
仕込みなし：100件かけて、受付で95件止まる
仕込みあり： 30件かけて、受付を10件突破する
```

### 架電の時間帯

| 時間帯 | 業種 |
|---|---|
| 8:30〜9:30 | 建設・工務店（現場に出る前） |
| **10:00〜11:30** | **全業種の本命** |
| 12:00〜13:00 | 避ける（製造業は昼休みが早い） |
| 14:00〜16:00 | 介護・福祉 |
| **16:00〜17:00** | **第2の山** |
| 17:00〜 | 建設（社長が戻る時間） |

## この設計から得た一般則

**v1・v2の失敗から出た、今後どの商材でも使えるルール。**

1. **既存ツールの標準機能を先に調べる。** 意外性の前に、被りの確認。
2. **「◯◯をAIで」と言えてしまう業務は、たいてい既にツールがある。** 言えないものを探す。
3. **手順ではなく判断を狙う。** 手順は誰かがツール化している。判断はまだ誰もできていない。
4. **断られたら「どちらのツールですか？」と聞く。** それが次の設計の材料になる。
